# Money

App de gestão financeira pessoal. React + Vite + TypeScript + Tailwind CSS v3, Supabase (Postgres + Auth + RLS) como único backend. Deploy em Vercel: https://money-app-woad.vercel.app

## Rodando localmente

```bash
npm install
cp .env.example .env   # preencher VITE_SUPABASE_URL e VITE_SUPABASE_ANON_KEY
npm run dev
```

Banco: ver `sql/README.md` para o passo a passo (rodar `sql/001` a `sql/008` em ordem no SQL Editor do Supabase).

## Estrutura

```
src/
  app/AppShell.tsx        Sidebar (desktop) + BottomNav (mobile) + Outlet
  features/auth/          AuthProvider, ProtectedRoute/AdminRoute/PublicOnlyRoute, AuthLayout
  components/ui/          primitivos (Button, Card, Input, Select, Modal, Badge, Toast, Sidebar, BottomNav...)
  components/finance/     componentes de domínio (BalanceCard, TransactionForm, AccountCard, GoalCard, gráficos...)
  pages/                  uma página por rota (Dashboard, Transactions, Categories, Accounts, Reserves, Loans, Reports, Profile, admin/AdminPage)
  lib/                    supabase.ts, format.ts (dinheiro em centavos), accountTypes.ts, insights.ts, invoices.ts (fatura de cartão), authErrors.ts (traduz erros do Supabase Auth), chartColors.ts, queries/*.ts (hooks React Query — queries e mutations juntas por domínio)
  types/database.ts       tipos espelhando o schema do Postgres
sql/                      migrações numeradas (001 a 008), rodar manualmente no SQL Editor do Supabase — não há CLI configurado
```

## Decisões importantes

- **Dinheiro sempre em centavos** (`amount_cents`, `balance_cents` etc., `bigint` no banco). Formatação em `lib/format.ts`.
- **Saldo da conta é uma coluna mantida por trigger** (`accounts.balance_cents`), não uma soma calculada em tempo real — é isso que permite apagar detalhe de movimentações com mais de 6 meses (retenção) sem perder o saldo. Ver `sql/002` e `sql/007`.
- **Movimentações e transferências futuras só entram no saldo quando o usuário confirmar manualmente — nunca sozinhas só porque a data chegou.** Coluna `transactions.applied_to_balance` (e `transfers.applied_to_balance`) controla isso. No INSERT, o trigger só confirma automaticamente se `coalesce(due_date, date)` já é hoje ou passado (ou seja, é um lançamento de algo que já venceu/aconteceu); em qualquer UPDATE, o trigger **nunca recalcula a partir da data** — só respeita o valor explícito de `applied_to_balance` enviado pelo cliente. A confirmação manual é feita pela mutation `confirm` em `useTransactionMutations()` (usada pelo botão "Já paguei/Já recebi — confirmar" no `TransactionForm`), que envia `applied_to_balance: true` explicitamente; `unconfirm` desfaz. Ver `sql/007` (mecanismo original), `sql/009` (removeu o cron diário `money-apply-due-transactions` e o recálculo automático no UPDATE — o usuário não queria confirmação automática nem para despesas nem para receitas) e `sql/012` (INSERT passou a considerar `due_date`, não só `date`). Itens não confirmados aparecem como selo clicável "Pagar/Vencido" (despesa) ou "Receber/Atrasado" (receita) do lado do valor, nas listas de movimentações — tocar confirma ou desfaz.
- **`transactions.date` vs. `transactions.due_date`** (sql/011): `date` é quando a movimentação foi registrada/aconteceu; `due_date` (opcional) é quando ela vence de fato, quando diferente de `date` — útil pra lançar hoje uma conta com vencimento futuro. `lib/invoices.ts` (`transactionDueDate`) calcula o vencimento efetivo de qualquer movimentação, em ordem: `due_date` explícito → vencimento da fatura se for compra em cartão de crédito (via `closing_day`/`due_day` da conta) → senão a própria `date`. O formulário só mostra o campo "Vencimento" para contas que não são cartão (cartão calcula sozinho e mostra em `invoiceHint`). Empréstimos têm o mesmo padrão (`loans.due_date`, sql/010), só que ali é puramente informativo (não afeta o trigger de saldo do empréstimo, que é por valor).
- **Movimentações mostra só o que está em aberto; o quitado vai para Relatórios.** `isTransactionSettled` (`lib/invoices.ts`): em conta comum é `applied_to_balance`; em compra de cartão é "a fatura dela já foi paga" (transfer com o `invoice_period`). Relatórios tem a seção "Movimentações quitadas" (por período) onde dá pra editar ou desfazer a confirmação — o item volta pra Movimentações. Empréstimos são editáveis (`sql/013`: o trigger de UPDATE reajusta o saldo, incluindo pagamentos já registrados).
- **Relatórios contam cada movimentação no mês do VENCIMENTO efetivo** (`transactionDueDate`: vencimento informado → vencimento da fatura, se for compra no cartão → `date`), a mesma regra do filtro de Movimentações: `monthOf()` em `pages/Reports.tsx` alimenta cards, gráfico mensal, distribuição por categoria, lista de quitadas e (via `byPaymentMonth`, que troca a `date` pelo vencimento) os insights. Assim, para o mesmo mês, o total de Movimentações (só em aberto) e o de Relatórios (aberto + quitado) partem do mesmo critério e só diferem pelo que já foi quitado. A lista de quitadas ainda exibe a data real da compra. **Papéis das telas: Dashboard = presente + previsão próxima; Relatórios = análise detalhada do histórico.** Dashboard (`pages/Dashboard.tsx`): card de saldo simples (ver seção "Card de saldo do Dashboard"); "Próximos vencimentos" (30 dias + atrasados) lista contas em aberto e faturas de cartão não pagas. O selo "+x% vs. mês anterior" foi removido (comparava acumulado de receitas−despesas, não o saldo). "Evolução do saldo" continua por `date`. Relatórios: cada período soma realizado + em aberto pelo mês do vencimento, e a **Taxa de economia** é sempre rotulada — "Projetada" (inclui o em aberto, com o valor a receber/a pagar explícito e a taxa só do realizado) ou "Realizada" — e vira "—" quando não há receita (nunca "0%"/"economizou X% da renda"). Cards de receitas/despesas mostram "Em aberto: R$ x". Se dois totais "não batem", primeiro confira se a aba está com a versão antiga (o app é SPA: aba aberta antes de um deploy só atualiza com refresh).
- **Cartão de crédito não soma no "Saldo total"** (`totalLiquidBalanceCents` em `lib/accountTypes.ts` exclui `type: 'credit_card'`). O card do cartão mostra "Fatura atual" (`currentInvoiceByAccount`, que usa `closing_day` quando cadastrado, senão cai para soma do mês civil), não o `balance_cents` bruto.
- **Carência de 3 meses na limpeza (sql/031, decisão do usuário)**: quem está pagando mantém o histórico do PLANO (Start/Plus 6 meses, Pro 24, Premium ilimitado), mesmo sem usar o app. Assinatura vencida conta como "em dia" por 3 meses depois do vencimento; passados os 3 meses (conta ABANDONADA: último acesso = maior entre `paid_until`, `trial_ends_at` e `created_at` há mais de 3 meses, sql/032), `cleanup_old_transactions()` apaga TODOS os lançamentos da conta (login, contas, categorias, metas e saldos ficam). Vitalício e admin nunca são limpos. O texto abaixo descreve a regra de quitação/saldo, que continua valendo para o que é apagado.
- **Retenção de 6 meses**: `cleanup_old_transactions()` apaga as `transactions` com `date` mais antiga que 6 meses (pela `date`, não pelo vencimento) que já foram QUITADAS — conta comum: `applied_to_balance`; cartão: fatura já paga (sql/016); o que ainda não foi pago é preservado sem limite de idade. Roda dia 1 de cada mês às 03:00; nunca toca profiles/categories/accounts/goals/goal_contributions/plans. O DELETE normal desfaz o saldo, então a limpeza liga a flag `money.skip_balance` (sql/015) para o trigger NÃO reverter — saldo sobrevive à limpeza. Funções de manutenção (`cleanup_old_transactions`, `apply_due_*`) têm EXECUTE revogado de anon/authenticated: por padrão o Supabase deixa toda função do schema `public` chamável via RPC, então funções `security definer` novas precisam de `revoke execute ... from public, anon, authenticated` (ou checar `is_admin()` dentro).
- **RLS em tudo**; `is_admin()` (security definer) dá acesso administrativo também no banco, não só no frontend. **RLS `user_id = auth.uid()` sozinho NÃO basta** (auditoria de segurança achou 2 furos reais): (1) `profiles_update_own` deixava o usuário mudar o próprio `role` → trigger `protect_profile_privileged_columns` (sql/017); (2) dava para inserir linha com o próprio `user_id` mas apontando `account_id`/`loan_id`/`goal_id` de OUTRA pessoa e os triggers `security definer` mexiam no saldo dela → trigger `a0_check_ownership` (sql/018) valida o dono de tudo que a linha referencia. Ao criar tabela/coluna nova que referencia outra tabela do usuário, incluir a checagem em `check_row_ownership()`; ao criar coluna sensível em `profiles`, incluir em `protect_profile_privileged_columns()`. Teste de segurança = 2 usuários descartáveis tentando ler/alterar/apontar para dados um do outro.

- **Fatura de cartão real** (sql/008): `accounts.closing_day`/`due_day` definem o ciclo. `lib/invoices.ts` (`getInvoicePeriod`, `groupTransactionsByInvoice`) decide em qual fatura cada compra cai (dia do fechamento ou depois → fatura seguinte; antes do dia de fechamento → fatura que fecha neste mês. Ex.: fechamento dia 1 → tudo de 01/10 a 31/10 cai na fatura que fecha em 01/11 e vence no `due_day` dela; sql/027 alinha a limpeza de histórico a essa regra) e calcula o vencimento. Nunca se cadastra o valor total da fatura — cada compra é uma `transaction` normal (com categoria/data/parcelas); a fatura é só um agrupamento derivado, exibido no `InvoiceModal`. Na lista de Movimentações, compra em cartão nunca mostra o selo Pagar/Vencido (não existe confirmação por item — quem "quita" é a fatura inteira); mostra só a data da compra e, quando o vencimento da fatura é diferente, um selo "Fatura vence DD/MM" ao lado. O filtro De/Até de Movimentações (e os atalhos "Este mês"/"Próximo mês") filtra pelo vencimento efetivo (`transactionDueDate`), não pela data bruta — por isso é aplicado no cliente (não dá pra fazer isso via `.gte`/`.lte` do Supabase, já que o vencimento de uma compra em cartão é calculado, não uma coluna).
- **Pagar uma fatura = uma `transfer`** da conta escolhida para o cartão, marcada com `invoice_period`. Isso não conta como despesa nos relatórios (as compras já contaram na hora); evita duplicar despesa. Uma fatura é "Paga" quando existe uma transfer com esse `invoice_period` para aquele cartão — pagar antes do vencimento já resolve o "pago antecipado" (não precisa de lógica extra).
- **Transferências** (tabela `transfers`, sql/008) e **empréstimos** (`loans`/`loan_payments`, sql/008) têm seu próprio trigger que ajusta `accounts.balance_cents` direto — nunca criam linhas em `transactions`, então nunca aparecem em receitas/despesas dos relatórios. Transferências respeitam `applied_to_balance` (mesma lógica de data futura que `transactions`); empréstimos são sempre imediatos (sem agendamento).
- **Quitação de empréstimo é pelo total da pessoa, não lançamento por lançamento.** No modal da pessoa (`pages/Loans.tsx`, `PersonLoanCard` → abre por `openPerson`), além de "Quitar tudo" (todos os empréstimos pendentes daquela direção de uma vez), existe "Registrar pagamento (valor parcial)": a usuária digita um valor e ele é distribuído automaticamente entre os empréstimos da pessoa na mesma direção, do vencimento/data mais antigo para o mais novo (`partialAllocation`, FIFO), até acabar o valor — sem precisar abrir cada lançamento. Se a pessoa tem empréstimo nas duas direções (emprestei e peguei), um seletor "Recebi/Paguei" aparece antes do campo de valor, porque pagamento parcial só faz sentido numa direção por vez. Os dois fluxos (quitar tudo e parcial) usam a mesma mutation `payOff` (`useLoans.ts`, insert em lote de `loan_payments` — tudo ou nada), que já aceita valores por empréstimo diferentes de "pendente total", então um pagamento parcial de um lançamento específico continua possível via "Registrar pagamento" dentro do detalhe de UM empréstimo (`detail`), que é outro fluxo, mais granular.
- **Conta do pagamento de empréstimo** (sql/028): `loan_payments.account_id` diz em qual conta o recebimento/pagamento cai (nulo = a conta do empréstimo, como antes). No modal da pessoa há um seletor único ("Receber na conta"/"Pagar com a conta"/"Conta do pagamento") usado por "Quitar tudo" e pelo pagamento parcial; o detalhe de um empréstimo tem o seu. Cartão de crédito não aparece na lista. O front só envia `account_id` quando difere da conta do empréstimo (assim funciona mesmo antes de rodar a 028). Editar/excluir o empréstimo desfaz cada pagamento na conta onde ele caiu.

## Design system — "Aurora Glass"

Dark-only. Fundo é um gradiente aurora fixo (`.app-aurora` em `index.css`, renderizado uma vez em `App.tsx`) atrás de tudo; as páginas em si não têm cor de fundo sólida. Cards usam a classe utilitária `.glass` (vidro fosco, `backdrop-filter: blur`) por padrão — é o piso, não o destaque. Brilho (`.glow-ring` / prop `glow` no `<Card>`) é reservado só para o elemento mais importante de cada tela (saldo no Dashboard, card do usuário no Perfil). Tipografia: `font-display` (Space Grotesk) em títulos de página e números grandes, `font-sans` (Manrope) no resto. Paleta em `tailwind.config.js` (`brand`, `violet`, `ink`, `danger`) — cores de gráfico validadas para acessibilidade (contraste/daltonismo) ficam em `lib/chartColors.ts`, não reusar hex soltos em gráficos novos sem rodar o validador da skill `dataviz`.

**Cuidado ao usar opacidade em tokens customizados**: `bg`, `surface`, `border`, `danger.soft` etc. são strings `rgba(...)` fixas no config, não hex. Aplicar um modificador de opacidade do Tailwind neles (ex.: `bg-surface/90`) quebra silenciosamente (renderiza branco sólido) — já aconteceu no BottomNav e no Toast. Para vidro/transparência use a classe `.glass` ou o token já pronto, nunca `/NN` em cima desses tokens.

## Cada tela tem uma métrica-âncora no topo

Dashboard (saldo total + insights), Movimentações (total do período + contador), Categorias (contagem), Contas (saldo líquido total), Reservas (acumulado total), Empréstimos (total emprestado), Relatórios (taxa de economia), Admin (nº de usuários) — ao adicionar uma tela nova, manter esse padrão.

## Card de saldo do Dashboard

`BalanceCard` é propositalmente simples, a pedido da usuária (ela rejeitou duas versões com mais informação — barra de progresso/previsto em caixa e depois previsto + a receber/a pagar): só **Saldo total** (realizado, sem cartão) e dois quadros **Receitas do mês / Despesas do mês** com o total do MÊS ATUAL pelo vencimento (quitado + em aberto que vence no mês; `income.doneCents + openCents` em `pages/Dashboard.tsx`). Sem linha de previsto, sem 'a receber/a pagar', sem percentual vs. mês anterior. Não acrescentar informação nesse card sem ela pedir; detalhes de aberto/atrasado ficam em 'Próximos vencimentos' e nos Relatórios.

## Insights do Dashboard

`lib/insights.ts` (`computeInsights`) gera no máximo 3 observações reais (nunca inventadas) a partir dos dados: fatura de cartão perto do limite, categoria que mais subiu vs. mês anterior, total de recorrências do mês, variação da taxa de economia. Cada insight só aparece se houver dado suficiente para sustentá-lo.

## Autenticação e segurança

- Todo `<Input type="password">` já tem o botão de mostrar/ocultar embutido (não precisa reimplementar por tela).
- Erros do Supabase Auth vêm em inglês — sempre passar por `lib/authErrors.ts` (`translateAuthError`) antes de exibir ao usuário; nunca mostrar `error.message` puro numa tela de auth.
- **"Manter conectado"** (caixinha no login, desmarcada por padrão; `lib/sessionPolicy.ts`): sem marcar, o app sai da conta depois de 30 min sem uso — conferido ao abrir (`AuthProvider`, antes de mostrar dados), ao voltar para a aba e a cada minuto; uso = toque/tecla/rolagem, gravado em `localStorage` (`money.lastActive`, compartilhado entre abas). A saída usa `signOut({ scope: 'local' })` e o login mostra "saímos da sua conta depois de 30 minutos sem uso". Quem marca, ou entrou antes da opção existir (sem `money.remember` salvo), segue conectado. Cadastro/link do e-mail não passam pela caixinha, então ficam conectados.
- **Aviso de versão nova** (`components/ui/UpdateBanner.tsx`, em `App.tsx`): a cada 5 min e ao voltar para a aba, busca `/index.html` sem cache e compara o arquivo `/assets/index-*.js` com o carregado; se mudou, mostra "Nova versão disponível · Atualizar" (recarrega). Resolve aba/app instalado aberto antes de um deploy.
- Login tem bloqueio client-side após 5 tentativas erradas (30s de espera) — é só uma camada extra de UX; a proteção real contra força bruta é do próprio Supabase Auth (rate limit por IP no servidor). Para reforçar mais, habilitar CAPTCHA (hCaptcha) em Authentication → Settings no painel do Supabase.
- Sincronização entre dispositivos já funciona nativamente (todo dado vem do Postgres via Supabase, nunca de localStorage) — testado logando na mesma conta em dois contextos de navegador simultâneos. Não há realtime (push instantâneo); os dados atualizam ao navegar/recarregar a tela, não durante uma sessão aberta em outro aparelho.
